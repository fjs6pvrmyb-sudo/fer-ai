# Fase 6A · Contrato fiscal offline

El módulo prepara XML sintético sin firma. Atiende factura ordinaria `01` con receptor ficticio y tiquete ordinario `04` sin receptor, en CRC con dos decimales, IVA 13 % y pago completo registrado en la transacción de venta. La prueba modela un precio final **con IVA incluido** de ₡1.130 y declara por separado la base de ₡1.000 y el IVA de ₡130. Identificaciones, actividad, ubicación y nombres se usan como fixtures estructurales. Su registro ante Hacienda queda fuera de la verificación.

## Contrato y límites

- El catálogo fiscal se vincula a la versión de precio que quedó registrada en la venta. La base unitaria se declara explícitamente con hasta cinco decimales. El módulo concilia cada línea y el total fiscal con los céntimos de la venta. `iva13` es el único tratamiento aceptado. Una configuración sin CABYS o IVA bloquea la reserva. El CABYS `8310100000000` se tomó del fixture exacto TE de Dojo. La tabla conserva la referencia y versión del fixture. Esta procedencia habilita la prueba local y queda pendiente cotejar el catálogo oficial vigente y el tratamiento real por producto. [Fixture del SDK fijado a `v0.13.0`](https://github.com/DojoCodingLabs/hacienda-cr/blob/v0.13.0/packages/sdk/src/__fixtures__/exact-te.ts)
- FER AI registra `cash`, `card` y `transfer`. La prueba asigna códigos `01` y `02` a efectivo y tarjeta. Para cada `transfer` exige declarar `bank_transfer` (`04`) o `sinpe_movil` (`06`) por identificador de pago de esa venta. Agrupa los importes por código a partir de los cobros registrados. La coincidencia depende del pago original de la venta. Una venta parcial, a crédito o liquidada posteriormente queda fuera del caso contado de 6A.
- El SDK `@dojocoding/hacienda-sdk@0.13.0` usa Node 22+ y se probó en Node 24 con los exports exactos de factura y tiquete. Los importes se pasan como texto y se comparan con `BigInt`. El SDK admite cinco decimales monetarios y hasta `9999999999999.99999` por importe. El núcleo conserva su escala operativa de dos decimales para este caso. `validateDocumentXml()` comprueba estructura e identidad contra el XSD 2026 incluido. La conformidad de una firma, la aceptación de Hacienda, el tratamiento tributario y la vigencia oficial son comprobaciones independientes.
- El módulo funciona desde Node contra un Supabase de loopback. El cliente rechaza destinos remotos y redirecciones. La app Next sigue sin exponer una ruta fiscal. Las pruebas unitarias impiden cualquier `fetch` durante el render y la validación XSD. El módulo no carga un cliente de Hacienda ni usa credenciales fiscales, certificados o PIN.

## Persistencia y límites de acceso

| Tablas                                                        | Responsabilidad                                                                                                                                                                               |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fiscal_issuers`, `fiscal_organization_settings`              | Identidad canónica por tipo y número, vinculación por organización, proveedor de sistemas, actividad, sucursal, terminal y activación offline explícita.                                      |
| `fiscal_cabys_fixtures`, `fiscal_product_profiles`            | Procedencia sintética, CABYS, unidad y clasificación, base fiscal por versión de precio y declaración explícita de IVA incluido.                                                              |
| `fiscal_series`, `fiscal_intents`                             | Reserva atómica por emisor canónico, ambiente, tipo, sucursal y terminal. Una intención original por venta y empresa, aunque un reintento cambie el tipo. Solicitud e instantánea inmutables. |
| `fiscal_documents`, `fiscal_history`, `fiscal_offline_status` | XML preparado, clave, consecutivo, SHA-256 y totales exactos. Historial con actor y hora. La vista distingue `reserved_offline` y `prepared_offline`.                                         |

La primera transacción reserva el consecutivo y fija el momento, el código de seguridad, el emisor, el receptor, los datos de catálogo y los pagos. La segunda persiste el XML y el evento de preparación juntos. Un reintento idéntico recupera el mismo documento. Uno que cambia el tipo, receptor o clasificación de pagos se rechaza. Si la ejecución se interrumpe tras reservar, se puede reanudar con la misma instantánea y número. La corrección de una reserva con configuración inválida requiere un flujo posterior con historial de anulaciones o sustituciones offline.

El cliente valida la sesión y las funciones verifican de nuevo la membresía activa de administrador o gerente. RLS y las claves foráneas compuestas aíslan el acceso. Solo el cliente privilegiado del fixture local puede invocar los RPC de preparación. La migración impide escrituras directas sobre intenciones, documentos e historial y añade disparadores contra edición y borrado. En una etapa con despliegue, el worker deberá usar un permiso acotado y separado del acceso general de servicio. Las tablas del núcleo se leen para construir la instantánea. Ventas, pagos y cierres conservan sus propios contratos y transacciones.

## Reproducir la prueba

1. Usá una copia desechable del árbol actual que incluya la migración `20261120000600_fiscal_offline.sql`. Instalá con `npm ci`. Configurá un `project_id` diferente en la copia de `supabase/config.toml`. Usá, por ejemplo, los puertos `55321` para API, `55322` para PostgreSQL y `55320` para shadow. Arrancá Supabase local y comprobá que las siete migraciones se aplicaron.
2. Creá `.env.local` dentro de la copia con `NEXT_PUBLIC_SUPABASE_URL` en `http://127.0.0.1:55321`, las claves publicable y de servicio del **Supabase desechable** y una contraseña temporal. `npm run demo:seed` prepara las cuentas ficticias. Las claves de Supabase solo autentican esta prueba local.
3. Ejecutá `npm test` para unitarias. Ejecutá `FERIA_FISCAL_DISPOSABLE_URL=http://127.0.0.1:55321 FERIA_FISCAL_OUTPUT_DIR=/ruta/temporal npm run test:fiscal` para preparar los dos XML. La prueba rechaza el puerto de API habitual `54321`. Ejecutá la regresión del núcleo antes de generar las ventas fiscales, para conservar los estados que esperan las pruebas de navegador.
4. Revisá `factura-ficticia-sin-firma.offline.xml` y `tiquete-ficticio-sin-firma.offline.xml`. Estos son artefactos de ejecución del fixture. Detené solo la pila desechable al terminar.

## Condiciones para la siguiente etapa

- **Firma local.** Aprobación separada, certificado y PIN sintéticos, almacenamiento temporal, prueba de XAdES-EPES y validación del XML firmado. Probar XML alterado, certificados vencidos, pin incorrecto y ausencia de secretos en logs. Revisar control de acceso al firmante y la inmutabilidad de los bytes firmados.
- **Sandbox autorizado.** Confirmar normativa, XSD y endpoint vigentes por fuentes oficiales. Acordar con el responsable fiscal el emisor, las series, las tarifas y los casos aceptados. Definir secretos por ambiente, cuotas, tiempos de espera, reconciliación de respuestas inciertas, custodia de XML y confianza de los certificados de respuesta. Habilitar la red e incorporar estados de Hacienda solo con autorización separada.
